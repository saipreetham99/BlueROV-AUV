01 · Overview

What this is

A matched pair of systems for a custom BlueROV2 (r1) underwater vehicle: a physics simulator built in Unity, and a real-vehicle control and telemetry stack. Both accept identical commands. Control strategies developed against the simulator deploy to hardware with no rewrite.

The vehicle, physically

  • Six thrusters. Four horizontal at 45° (vectored), two vertical. It can move forward, sideways, up, and rotate — without ever tilting.
  • Positively buoyant. Motors off, it floats up. A deliberate safety property, and the reason the depth controller needs an integral term.
  • Self-righting. Centre of buoyancy sits above centre of gravity, so it rolls back upright on its own. Hardware solving a software problem.
  • Raspberry Pi 4B onboard. All heavy computation happens topside; the Pi is a fast, dumb I/O bridge.
  • Tethered Ethernet. Everything between laptop and vehicle is UDP.

The competition task

Two identical submarines start in a pool facing away from each other. Each carries AprilTag markers on its back. You must find the other vehicle, get behind it, and read as many unique tag IDs as possible.

Understanding why that is hard explains most of the autonomy design. To read the opponent's tags you must get behind it. The opponent is doing the same to you, which means it keeps its nose pointed at you — which means its back stays pointed away. If both run a naive "face the target and circle" policy, they counter-rotate forever and neither ever scores. It is a stable deadlock.

Every "anti-stall" mechanism in this codebase exists to break that deadlock

The approach offset, the post-flip dash, and the three-phase reset manoeuvre are all answers to the same geometric problem. See Autonomy brain.

02 · Architecture

How data moves

Perception and decision-making live topside where there is a real CPU, a screen, and a debugger. The vehicle receives commands and returns observations. Nothing more.

Live · System data flow packets in transit
Three independent UDP streams. Command packets flow down, video and telemetry flow up. The simulator subscribes to exactly the same command port — which is what makes the strategy portable.

Why the vehicle is deliberately stupid

  • Iteration speed. Restarting a topside Python app takes two seconds. SSH-restarting something on a sealed vehicle takes minutes, and pool time is the scarcest resource in the project.
  • Vehicle code changes almost never, so its reliability compounds across seasons.
  • Debugging. You cannot attach a debugger to something two metres underwater.

The trade: autonomy dies if the tether dies. For a tethered pool competition that is the right call. The migration path is already clear — the strategy brain contains no networking at all, so it could move onto the Pi unchanged.

03 · Concepts primer

Six ideas you need first

Skip anything familiar. Each of these exists here because a specific design decision cannot be understood without it.

Degrees of freedom, and body frame

A rigid body has six degrees of freedom. This vehicle commands four: surge (forward), strafe (sideways), heave (up), and yaw (turn). Pitch and roll are left to physics — the self-righting buoyancy arrangement keeps them near zero with no control effort.

All four commands are body frame: surge = +1 means "go where your nose is pointing," not "go north." Depth is world frame. Confusing the two is the most common source of sign bugs in robotics, and it is why the simulator is full of InverseTransformDirection calls — forces are computed in hull coordinates because drag depends on which face meets the flow, then applied in world coordinates because that is what the physics engine wants.

PWM: how a number becomes thrust

An ESC (electronic speed controller) reads a pulse repeated 50 times a second. The width of that pulse is the command — a legacy of hobby servo protocol, which is why 1500 appears as a magic number throughout this codebase.

Live · PWM pulse train drag to change the command
Command 1500µs
Neutral sits in the middle of the range, not at zero. Generating six of these precisely is hard real-time work, and Linux is not a real-time OS — so the Pi offloads it to a dedicated PCA9685 chip and only writes new widths into its registers. Consequence: the chip keeps doing whatever it was last told. If topside software crashes, motors keep running. That is why the watchdog is not optional.

Why UDP, and why every stream drains to the newest packet

TCP guarantees delivery by retransmitting, which stalls everything behind a lost packet. For a control link that is exactly wrong — a 200 ms-old thruster command is worthless. You do not want it retransmitted, you want it discarded and replaced.

This shapes the code in two visible ways:

  • Every message is complete state, never a delta. Each thruster packet carries all six motors plus the light. Lose one and the next fully corrects you.
  • Receivers drain to the newest. Unity renders at ~60 fps while the control loop runs at 50 Hz; without draining, the socket buffer accumulates and latency grows without bound.
run_sim.py — drain to latestwhile True:
    try:
        data, _ = recv.recvfrom(64)
        if len(data) == struct.calcsize(BBOX_FMT):
            latest = data          # keep overwriting; only the last survives
    except BlockingIOError:
        break                      # socket empty, stop

Feedback control: P, I, deadband, windup

Two problems here are feedback problems: hold this depth, hold this heading. The P term pushes harder the further off you are, but leaves a steady-state error whenever a constant force opposes you. Here that force is positive buoyancy — the vehicle always wants to float. The I term accumulates error until it wins, effectively learning the buoyancy bias.

Two failure modes are handled, and the way they differ between the two loops is the most instructive thing in the control code: 

client — the same deadband, two different treatments# DEPTH hold: inside the band, FREEZE the integrator (keep its value)
if dt > 0.0 and abs(err) >= HOLD_DEADBAND:
    self._hold_i += err * dt
# ...the integral term is still applied, every tick.

# YAW hold: inside the band, DUMP the integrator and command nothing
if abs(err) < YAW_HOLD_DEADBAND:
    self._yaw_hold_i = 0.0
    return 0.0
Whether to keep or dump an integrator depends on the disturbance

Depth fights a constant load (buoyancy), so the accumulated value is useful information — throw it away and the vehicle drifts up immediately. Yaw has no constant load; water does not push you around a vertical axis. Any accumulated yaw integral is windup from the slew you just finished, and keeping it would make the vehicle rotate past target.

Hydrodynamics: why underwater ≠ air

Four forces matter, and they are exactly the four terms in Hydrodynamics.cs. The one that surprises people is added mass: to accelerate underwater you must also accelerate the water that has to get out of your way. For a blunt object like this it is comparable to the vehicle's own mass — 12.7 kg of added mass sideways.

A simulator ignoring it shows a vehicle accelerating roughly twice as fast as reality, and no amount of thrust tuning fixes that, because the error is in the shape of the acceleration curve rather than its scale. Added mass is also anisotropic — pushing this box nose-first is far easier than broadside.

I²C and SPI

I²C — two wires, each chip has a 7-bit address. Slow-ish (100 kHz–1 MHz here) but many devices share two wires. You can scan the bus and see which addresses answer, which is your first diagnostic when a sensor disappears.

SPI — four wires, faster (10 MHz here), full duplex, one chip-select per device. The detail that bites people:

xferdata[0] = reg | 0x80   # set the top bit => this is a READ

There is no separate read command in SPI. The high bit of the register address meaning read-vs-write is convention, not protocol — forget it and you silently write to the register you meant to read.

struct packing and endianness

packet = struct.pack("<7H", fl, fr, rl, rr, v1, v2, light)   # → exactly 14 bytes
  • < — little-endian, least significant byte first. Both ARM and x86 are natively little-endian, so neither side pays a byte swap.
  • 7H — seven unsigned 16-bit integers. Range 0–65535; pulse widths are 1100–1900, so 16 bits is ample.
  • 14 bytes is far below any MTU, so this packet can never be fragmented.

Three defences against FSM chattering

The cost of a state machine is flipping between two states when a condition sits on its threshold. This codebase defends three ways, and all three are worth copying:

  1. Grace periods — a timer must expire before a state change (grace_s = 0.5).
  2. Hysteresis — separate enter and exit thresholds. Using one threshold for both directions is how you build an oscillator by accident.
  3. Coasting on stale data — during the grace window, keep steering on the last known observation rather than going blind.

PCA9685 — integers to pulses

The chip counts ticks from a clock; one 4096-tick sweep is one PWM period. Critically, this driver uses an external 24.567 MHz clock, not the internal 25 MHz oscillator — you can see MODE1_EXTCLK being set. So for 50 Hz: 

prescaler = round(24.567e6 / (4096 × 50)) − 1
          = round(119.956) − 1
          = 119   (0x77)
The older wiki says 121 — that is wrong for this driver

121 is the answer for the internal oscillator. Every number in this document was recomputed from driver source.

Changing frequency requires a sleep-mode dance, and it contains one line that looks like dead code and is not:

pca9685.py — set_prescaler# 1. enter sleep (prescaler is write-protected while awake)
self.write(REG_MODE1, [MODE1_EXTCLK | MODE1_SLEEP | MODE1_AI])

# 2. undocumented but necessary: after entering sleep the output counters
#    are disabled until one of the output registers is written.
self.raw[0] = self.raw[0]

# 3. write the prescaler, then clear sleep
self.write(REG_PRESCALE, [prescaler & 0xff])
self.write(REG_MODE1, [MODE1_EXTCLK | MODE1_AI])

Delete step 2 and outputs go silent after any frequency change, in a way that looks exactly like a wiring fault. Every channel write is also read back and verified — a corrupted I²C write to a motor channel is a safety event, not a cosmetic one.

There is also a hardware kill: the chip's output-enable pin is wired to GPIO 26, active low. safe_shutdown() commands neutral first, waits 50 ms so those pulses actually go out, and only then disables the pin — because ESC behaviour on signal loss is manufacturer-dependent and not something to rely on.

MS5837 — depth from pressure

Six factory calibration coefficients live in the sensor's PROM and are CRC-validated at startup. If the CRC fails, the server disables the whole sensor thread rather than trusting garbage — a bad coefficient set produces plausible-looking wrong depths, which is far more dangerous than no depth.

Below 20 °C — i.e. any real pool — raw values pass through second-order polynomial correction. Skipping it introduces a temperature-dependent bias that looks like "depth hold drifts as the pool warms up over the afternoon." 

def depth(self):
    return (self.pressure(UNITS_Pa) - 101300) / (self._fluidDensity * 9.80665)

101300 is hard-coded sea-level atmospheric pressure. Real atmospheric pressure varies ±3 kPa with weather — about ±0.3 m of apparent depth. That is why the UI has a ZERO DEPTH button. Tare at the surface, work in relative depth, and the error cancels entirely. Never trust the absolute number.

ICM20602 — heading by integrating a gyroscope

The vehicle carries two magnetometers and the drivers for both are vendored here. Neither is used. Thrusters draw 60+ amps, and current through wiring inches from a magnetometer produces a field that swamps Earth's. Worse, the distortion is correlated with your own commands — turn harder and the compass lies more, in the direction you are turning. That is the most pernicious possible sensor failure for a control loop: it looks real and it reinforces the error.

So heading comes from integrating a gyro rate instead. The trade is unbounded drift, which is acceptable because matches last minutes and every use is relative. 

rov-server.py — HeadingTrackern, acc = 60, 0.0
for _ in range(n):
    acc += self.imu.read_all().g.z
    time.sleep(0.005)
self.bias = acc / n              # 60 samples over ~300 ms
...
rate = self.imu.read_all().g.z - self.bias
self.heading += rate * dt        # dt measured, not assumed
The vehicle must be physically still while the server starts

Those 300 ms become the bias for the entire session. Start while it is being carried or swinging on a tether and you bake motion into the bias, after which heading drifts steadily. The printed yaw-rate bias line is your check — expect a fraction of a deg/s.

What is deliberately not instrumented

There is no horizontal position measurement. No DVL, no acoustics, no overhead camera, no GPS. The vehicle knows its depth and relative heading, and nothing else about where it is.

Two consequences ripple through everything: surge and strafe distances during tuning are measured with a tape measure along the pool deck (that is the actual procedure, not a placeholder), and the autonomy is entirely reactive — no map, no waypoints, no dead-reckoned position. Given the sensor suite that is a feature: a position estimate from a drifting gyro and no velocity sensor would be confidently wrong within seconds, and a controller trusting it would be worse than one that never had it.

The contract between every component

Change anything here and you must change it in all of: the client, run_sim.py, pool_test.py, and ThrusterMixer.cs. There is no shared schema file — the format is duplicated by hand in four places.

Interactive · Thruster packet anatomy hover a byte
14 bytes total. struct.pack("<7H", …) — seven unsigned 16-bit integers, little-endian. Hover any byte.
< is little-endian, chosen because both ARM (the Pi) and x86 (the laptop) are natively little-endian so neither pays a byte swap. 7H is seven unsigned shorts. A JSON equivalent would be ~120 bytes and need parsing; this decodes in one instruction — and a fixed-width format cannot be partially valid, which is why len(data) != 14 is a complete validity check.

Video chunk size and the MTU question

Chunk size 60,000 sits just under UDP's 65,507-byte payload ceiling — but it is well above Ethernet's 1,500-byte MTU, so the IP layer fragments each chunk further. Losing any IP fragment loses the whole 60 KB chunk and therefore the whole frame.

Inference: a chunk size closer to the MTU (~1,400 bytes) would degrade more gracefully on a lossy link, at the cost of more packets. On a clean wired tether the current choice is fine and cheaper.

06 · Onboard server

Three threads, one job

~300 lines. Be a fast, boring, unkillable I/O bridge. Understand this file completely — it is the smallest and most safety-critical piece of the system.

Why three threads instead of one loop

Each subsystem blocks on something different and fails differently. The thruster thread blocks on a socket with a 20 ms timeout. The video thread blocks on cam.read(), which can hang for seconds on a USB glitch. The sensor thread blocks on ~40 ms I²C conversions and can raise on bus errors.

In a single loop, a camera stall would stall thruster commands, the watchdog would fire, and a perfectly healthy vehicle would go dead in the water because a webcam hiccuped. Threads make each failure local. Python's GIL means they do not run simultaneously on separate cores — but that is not the goal. The goal is that a blocking call in one does not block the others, and the GIL is released during I/O waits.

Graceful degradation, in a deliberate hierarchy

Result: the vehicle stays drivable in a degraded state. At a competition that is the difference between a bad run and no run.

The server does not clamp incoming pulse values

Whatever arrives in a valid-length packet goes straight to the PWM chip. The topside mixer guarantees 1100–1900, so this trusts the sender. Clamping to [1100, 1900] here would be two lines and would make the vehicle robust against a buggy or corrupted client. Recommended.

07 · Thruster mixing

The most-duplicated code in the repo

It appears in five places, and duplicating it was deliberate. Every copy must remain byte-for-byte equivalent. 

the mix — identical in Python and C#def mix(surge, strafe, heave, yaw):
    fl = clamp(surge - strafe - yaw)
    fr = clamp(surge + strafe + yaw)
    rl = clamp(surge + strafe - yaw)
    rr = clamp(surge - strafe + yaw)
    v1 = clamp(heave)
    v2 = clamp(-heave)
    return fl, fr, rl, rr, v1, v2

Read it by column to build intuition:

  • surge — all four horizontals same sign → net forward force, no torque.
  • strafe — because of the 45° mounting, fore-aft components cancel and lateral components add → pure sideways translation. This is the payoff of vectored thrusters.
  • yaw — a torque couple with no net force. Turns in place.
  • heave — the verticals get opposite signs because they are mounted in opposite orientations. Rebuild the vehicle with both facing the same way and this line must change, or heave will produce a violent roll.

Saturation, and why it must be replicated exactly

Full forward plus full right turn asks front-right for 2.0 and gets 1.0. The ratio between the pairs is preserved but the magnitude is not, and the asymmetry distorts the turn. That nonlinearity is unavoidable — but with advance_surge = 1.0 and dash_strafe = 1.0 in the current gains, the vehicle operates in saturation routinely, not as an edge case.

Had the simulator clamped differently — or scaled the whole command down proportionally, which is a defensible alternative design — any strategy tuned near full throttle would behave differently in water. Try it in the hero mixer.

The round trip through the simulator

SimBridge.cs inverts the mix to recover the original commands, and the inversion is deliberately lossy when something saturated: 

cmdSurge  = ( fl + fr + rl + rr) * 0.25f;
cmdStrafe = (-fl + fr + rl - rr) * 0.25f;
cmdYaw    = (-fl + fr - rl + rr) * 0.25f;
cmdHeave  = ( v1 - v2) * 0.5f;

If front-right clipped, the recovered commands are what the vehicle could actually execute, not what you asked for. Unity then applies forces matching the physically achievable command, exactly as real ESCs would. The saturation survives the round trip instead of being papered over.

Throttle scale

amp is the microsecond swing corresponding to a full-scale ±1.0 command — the system's master gain. The operator sets it as a percentage, and amp never appears on screen or in a log. Good design, with one arithmetic problem:

Real bug — throttle saturates at 66.7 %

AMP_FULL_SCALE = 600 but AMP_MAX = 400. Type 80 % and it clamps to 400, then displays back as 66.7 %. The top third of the throttle range does not exist.

The qualifier variant sets AMP_FULL_SCALE = 400.0 and is self-consistent — so the same displayed number means different physical thrust in two files in this repo. Before changing it: note that switching 600 → 400 rescales every throttle number in every historical log and every operator's muscle memory by 1.5×. Do it once, deliberately, and not the night before a competition.

Do not import torch in the main process

Not for a type hint, not for a version check. Torch, OpenCV, and SDL2 each ship native libraries and thread pools; mixing forked copies of them segfaults. That is why the worker uses mp.get_context("spawn") — a brand-new interpreter rather than a copy of the current one. This was clearly learned the hard way.

The second reason for a process rather than a thread is the GIL: neural network inference is long and CPU-bound, so as a thread it would freeze the operator display in visible chunks.

The queue discipline

Both IPC queues are maxsize=1 with explicit drop-stale logic on each side. The semantics are a mailbox holding the newest item, not a buffer. If the detector is slower than the camera, frames are dropped rather than queued — a queue would grow, and every element in it adds latency, so the detector would be analysing progressively older images while claiming to be current. Same principle as the UDP drain.

Event-driven control

The old design ran a fixed 30 Hz timer, sampling whatever box happened to be current. Because the timer was unsynchronised with detection arrival, the box had a random age between zero and one full detection period — measured at ~31 ms average. 

the current loopWAIT_TIMEOUT = 0.1
self.video.box_event.clear()          # ignore a stale pre-start signal
while self.autonomous and not self.abort:
    self.video.box_event.wait(timeout=WAIT_TIMEOUT)
    self.video.box_event.clear()
    ...one control step on the fresh box...

Box age at the moment of control drops to single digits. dt becomes real measured elapsed time, which is what the strategy's timers want anyway. And the timeout is the keep-alive floor: if video stalls the loop still ticks at 10 Hz, so the vehicle keeps searching and stays inside the 0.5 s watchdog. Without it, killing the video feed would hang the thread in wait() forever.

Why 31 ms mattered: in a control loop, lag directly reduces the maximum stable gain — laggier perception forces softer gains, which makes tracking worse in a second, compounding way. And the jitter was worse than the delay; constant delay you can tune around.

    amt = max(0.0, min(1.0, (self.joy.get_axis(axis) - rest) / span))
    return 0.0 if amt < 0.05 else amt

Analogue triggers rest at either −1 or 0 depending on the pad, so rather than guess, the rest value is captured when the mode starts. Triggers then always read 0.0 released → 1.0 pressed.

Holds, guards, and signs

Depth hold is a controller with a target. The depth guard is a constraint no control path may violate. They are different things and they behave differently.

Three sign conventions are guesses until verified in water

Each is flagged in the source with an explicit "verify this" comment. Getting one wrong turns a stabiliser into a destabiliser — the loop drives away from target, faster and faster.

  • DEPTH_INCREASES_DOWN — tare at the surface, push the vehicle down by hand. On-screen depth must go more positive.
  • YAW_CW_IS_POSITIVE — with yaw hold off, command a turn-right and watch the yaw readout.
  • The strategy's yaw = -yaw_kp * err_x — place a target to one side; the vehicle must turn toward it.

Recognising a sign error: the behaviour is not "slightly off," it is divergent. If something runs away the instant you enable a hold, check the sign before touching gains.

def guard_heave(self, heave):
    d = self.effective_depth()
    if d is None:                              return heave
    if d >= self.depth_max:                    return max(heave, DEPTH_RECOVER)

10 · Autonomy brain

A pure function that decides everything

surge, strafe, heave, yaw, flash = strategy.update(box, dt, back_visible)
Four floats and a boolean out. No cameras, no networks, no Unity, no Pi.

The golden rule, from the module docstring

"This file must NEVER mention cameras, networks, Unity, or the Pi. It only ever deals with a bounding box coming in and four numbers going out."

Which means: the same file runs against Unity's projected box and YOLO's real box unmodified; it is trivially unit-testable; it could move onto the Pi tomorrow; and a learned policy can replace it by implementing one method. That last point is not a coincidence — the interface is exactly the shape of an RL policy.

Each state has its own behaviour and its own gains, so each is tunable in isolation. The current state name is drawn on the operator display and written into every log row — which turns "it behaved strangely" into "it was stuck in ORBITING for 40 seconds."

Three defences against chattering

The cost of a state machine is flipping rapidly between two states when a condition sits on its threshold. This codebase defends three ways, all worth copying:

  • Grace periods. A lost detection does not immediately change state; grace_s = 0.5 must expire first.
  • Hysteresis. Enter orbit above 3.5 % of frame, leave only below 46 % of that (~1.6 %). Using one threshold for both directions is how you build an oscillator by accident.
  • Coasting on stale data. During the grace window the controller keeps steering on the last known box, so a one-frame dropout produces no visible twitch at all.
coasting = (not box.is_valid
            and self.lost_timer <= self.grace_s
            and self._last_box.is_valid)
aim = self._last_box if coasting else box

aim drives all steering math. box — the live one — drives all state transitions. Steer on stale data, but never change your mind on stale data.

Two refinements worth noticing. The vertical direction alternates each reset, so repeated resets cannot pin the vehicle against the surface. And phase 3 turns the same way the follow-on search will:

Every rotation exposes your own tagged back for a moment. Turning one way then reversing exposes it twice. That is a competitive consideration encoded in a sign — the kind of thing you only find by playing the actual game.

grace_s (0.5) ≪ orbit_flip_s (10) < stuck_reset_s (20)
                                 search_timeout_s (8, post-contact only)

stuck_reset_s must exceed orbit_flip_s, or the reset fires before the direction flip has ever been tried and the cheaper remedy is never used.

Hot reloading

Every gain lives in strategy_gains.json, checked by mtime at the top of every update(). Slider drag to changed vehicle behaviour: ~150 ms plus one loop. That is the difference between tuning and guessing.

Why orbit gets its own gains

From the docstring: ORBITING "centres against a continuous sideways disturbance — its own strafe — that ADVANCING never sees, so it usually wants a softer gain than the chase does." Use the chase gain and it over-corrects into a left-right judder instead of a smooth circle. Current values are ~40 % softer, exactly as predicted. Missing keys inherit:

self.orbit_heave_kp = num("orbit_heave_kp", self.heave_kp)

SCANNING deliberately uses the advance pair instead — "nothing is strafing here, so there's no self-made disturbance to soften for." The same reasoning applied consistently in both directions, which is how you know it was reasoned rather than guessed.

  • Few false positives on walls, lane markers, tiles, reflections, divers.
  • Detects at the ranges that matter — far enough to acquire during a search, close enough to hold during an orbit.

12 · Unity physics

Four forces, one clever trick

The simulator exists because pool time is scarce and hardware is fragile. Its value is entirely proportional to how well it matches reality — which is why roughly half its code is a tuning harness rather than physics.

Axis convention — read this before touching anything

Translation (X, Y, Z) = (surge, heave, sway) and Rotation (X, Y, Z) = (roll, yaw, pitch). This is not standard marine convention — it is Unity's Y-up world mapped onto marine names. So addedMassLinear.y is heave, not sway. Index the wrong element and you will tune drag on an axis you are not testing.

Taking over from Unity's physics

rb.useGravity     = false;   // we apply weight ourselves, at the CG
rb.linearDamping  = 0f;      // Unity's damping is not physical; ours is
rb.angularDamping = 0f;

dryInertia = rb.inertiaTensor;      // capture BEFORE inflating
rb.inertiaTensorRotation = Quaternion.identity;

Unity's drag is a non-physical velocity multiplier — it cannot express the linear-plus-quadratic, direction-dependent behaviour real water has. And capturing dryInertia once is what makes Reinitialize() safe to call at runtime after loading tuned parameters: without that baseline, each call would add the added inertia on top of the previous result and compound.

Term 1 — restoring

Vector3 cg = rb.worldCenterOfMass;
Vector3 cb = cg + transform.up * centreOfBuoyancyHeight;   // 1 cm above
rb.AddForceAtPosition(Vector3.down * weight,   cg, ForceMode.Force);
rb.AddForceAtPosition(Vector3.up   * buoyancy, cb, ForceMode.Force);

Two equal, opposite forces at vertically separated points form a couple whenever the body tilts — so self-righting is free. With buoyancyFactor = 1.0 the net force is zero while the righting torque persists: force and torque decoupled by geometry alone, no controller needed. transform.up rather than Vector3.up is deliberate — the centre of buoyancy is fixed in the hull, so it rolls with the vehicle and the lever arm behaves correctly.

Terms 2 + 3 — the effective-mass trick

Real added mass is direction-dependent (5.5 kg forward, 12.7 kg sideways, 14.57 kg vertical). Unity's Rigidbody has one scalar mass. You cannot give it a mass tensor. The solution: leave mass alone and scale every applied force so the resulting acceleration comes out right. 

Unity computes:  a = F_applied / m
We want:         a = f_true    / (m + m_added)

So set:          F_applied = f_true × m / (m + m_added)
f.x *= rb.mass / (rb.mass + addedMassLinear.x);
f.y *= rb.mass / (rb.mass + addedMassLinear.y);
f.z *= rb.mass / (rb.mass + addedMassLinear.z);
rb.AddForce(transform.TransformDirection(f), ForceMode.Force);

Every translational force must go through this — damping, Coriolis, and thrust — hence the public AddBodyForce() helper. Torques must not. Angular added inertia was folded into the inertia tensor directly, so Unity already divides by it. Scaling torques too would double-count.

The damping law itself uses Abs(v) * v rather than v * v, which preserves sign so drag always opposes motion. Squaring directly would make backward drag accelerate you backwards.

Term 4 — Coriolis

When the vehicle translates and rotates at once, anisotropic added mass generates a sideways force and a torque. Zero for pure translation, zero for pure rotation — it only appears in combined motion, which is exactly what orbiting does continuously.

The comment is precise about scope, and that precision is why the term is correct rather than double-counted: real-mass Coriolis is handled by Unity's own solver, and rotational added-inertia coupling comes from the inflated tensor. What remains — and what is added here — is coupling from the anisotropic linear added mass.

No rendering — pure geometry. It projects the target's local mesh bounds, not the world axis-aligned box, because a world AABB around a pitched hull is much larger than its silhouette. The local box hugs the shape and rotates with the vehicle, matching what a real detector would produce. What the simulated camera does not model

It is a perfect, zero-latency, noise-free detector. No false negatives, no false positives, no motion blur, no turbidity, no inference delay. The real one has all of those — which is precisely why grace_s and the coasting behaviour exist, and why a strategy that looks flawless in sim can chatter in water.

Highest-value simulator improvement available: inject realistic detector imperfection — drop 5–10 % of boxes, add a few pixels of corner jitter, delay the send by your measured ctrl lag. That would make the sim exercise exactly the code paths that currently only get tested in a pool. It is also a prerequisite for any learned policy: an agent trained against a perfect detector will exploit that perfection and fall apart on real YOLO output.

Thread safety in SimBridge

Three details, all correct and worth copying:

  • lock (cmdLock) around every shared read and write — without it you could read cmdSurge from a new packet and cmdYaw from the previous one, producing a command that was never sent.
  • System.Environment.TickCount, not Time.time. Unity's Time API is main-thread only; calling it from the receive thread is undefined behaviour that manifests as rare, unreproducible crashes.
  • subLight.enabled assigned in FixedUpdate, never in the receive thread, because touching Unity objects off the main thread is likewise forbidden.

And a diagnosis that will save someone an hour: the bind-failure message says "a previous Play session may still hold it — restart the editor." Unity does not always release sockets on exiting Play mode.

Coriolis, as implemented

void ApplyCoriolis() {
    if (!enableCoriolis) return;
    Vector3 v = transform.InverseTransformDirection(rb.linearVelocity);
    Vector3 w = transform.InverseTransformDirection(rb.angularVelocity);

    Vector3 a1 = Vector3.Scale(addedMassLinear, v);    // added-mass linear momentum

    Vector3 fCor = -Vector3.Cross(w, a1);
    fCor.x *= rb.mass / (rb.mass + addedMassLinear.x);
    fCor.y *= rb.mass / (rb.mass + addedMassLinear.y);
    fCor.z *= rb.mass / (rb.mass + addedMassLinear.z);
    rb.AddForce(transform.TransformDirection(fCor), ForceMode.Force);

    Vector3 tCor = -Vector3.Cross(v, a1);
    rb.AddRelativeTorque(tCor, ForceMode.Force);
}

The 1-D model the solver bisects on

(float powered, float glide) Simulate(Axis a, float gain, float dragScale) {
    float dt = Time.fixedDeltaTime;
    bool yaw = (a == Axis.Yaw);
    float mEff, dragLin, dragQuad;

    if (yaw) {
        mEff     = rb.inertiaTensor.y;                    // includes added inertia
        dragLin  = hydro.dragLinearRotation.y * dragScale;
        dragQuad = hydro.dragQuadRotation.y   * dragScale;
    } else {
        float added = ai == 0 ? hydro.addedMassLinear.x       // Surge  → X
                    : ai == 1 ? hydro.addedMassLinear.z       // Strafe → Z (sway)
                              : hydro.addedMassLinear.y;    // Heave  → Y
        mEff = rb.mass + added;
    }

    float v = 0f, powered = 0f, t = 0f;
    while (t < testDuration) {                    // powered phase
        float drag = (dragLin + dragQuad * Mathf.Abs(v)) * v;
        v += (gain - drag) / mEff * dt;
        powered += v * dt;  t += dt;
    }
    float total = powered, tc = 0f;
    float stop = yaw ? StopYaw * Mathf.Deg2Rad : StopSpeed;
    while (Mathf.Abs(v) > stop && tc < MaxCoast) {  // glide phase
        float drag = (dragLin + dragQuad * Mathf.Abs(v)) * v;
        v += (-drag) / mEff * dt;
        total += v * dt;  tc += dt;
    }
    return (powered * scale, (total - powered) * scale);
}

13 · Sim-to-real tuning

Two measurements, two unknowns

This is the procedure that makes everything else trustworthy. Budget a full pool session.

Live · Step test — powered vs glide press run
Powered distance depends on thrust and drag. Glide distance depends on drag only — thrust is off. Two measurements, two unknowns, solvable. Report them as one combined number and the problem becomes underdetermined. This split is the single best idea in the tuning workflow.

The solver

TuningHarness.AutoMatch nests two bisections. The inner one solves for thrust gain that reproduces your measured powered distance, given a trial drag. The outer one adjusts drag until the glide matches. Both relationships are monotonic — more gain means further, more drag means shorter glide — which is exactly the condition under which bisection is guaranteed to converge. 

for (int i = 0; i < 40; i++) {
    scale = 0.5f * (lo + hi);
    gain  = SolveGain(a, realPowered, scale);        // inner: 40 more iterations
    float g = Simulate(a, gain, scale).glide;
    if (g > realGlide) lo = scale; else hi = scale;
}

1600 model runs, each simulating ~11 s at 50 Hz, executed offline in an instant — no Unity Play time, no pool time. The 1-D model replicates the same equation of motion at the same fixedDeltaTime, so the offline solver and live physics agree by construction, including their discretisation error.

Procedure per axis

  1. Real vehicle: run the step test 3–5 times and average. Depth and yaw are recorded automatically; surge and strafe need a tape measure.
  2. Simulator: run the same axis, type the averaged powered and glide values, press Auto-match.
  3. Run the axis again live to confirm — the solver matched a 1-D model, not the full 3-D simulation.
  4. Press Save params and commit Assets/parameters/sub_tuning.json.

Even when the true error is in a third parameter it cannot touch. A drag scale far from 1.0 — say above 3 or below 0.3 — is a signal that something upstream is wrong, not a result to accept.

What matching does not buy you

  • Tether drag. Not modelled at all, likely the largest unmodelled effect, and asymmetric — dragging the umbilical one way differs from the other. Tune with the tether configured the way you will compete.
  • Wall and floor effects, water currents, and the wake the other vehicle generates.
  • Motor asymmetry. Real thrusters produce more thrust forward than reverse; one gain per axis is a compromise the harness explicitly acknowledges.

Treat the simulator as very good for behaviour — does the FSM sequence correctly, do gains oscillate, does the deadlock break — and only approximate for absolute distances.

The dash strafes negative on the box-valid path and positive on the box-lost path. The surrounding comments describe the dash as being "in the new direction," which matches only one of them. Structural weaknesses

  • The protocol is duplicated in four places with the inverse in a fifth, and nothing enforces agreement. A change missed in one place produces a vehicle that behaves differently in sim than in water — the exact failure the architecture exists to prevent. Until it is fixed: any edit to the mix or packet format goes into all five sites in the same commit.
  • No automated tests. The brain is a pure function and would be trivial to test — feed synthetic box sequences, assert on state transitions and output signs. Highest-value missing infrastructure in the repo, by a distance.
  • Camera intrinsics are uncalibrated — an FOV-derived pinhole model with no distortion terms, in water, behind a dome port.

Environmental fragilities

  • Gamepad indices are not portable. Different pad, OS, or SDL version → different numbers. Run controller_id_tester.py after any change.
  • Both machines must launch from the credentials directory — the path is CWD-relative despite the expanduser call.
  • The vehicle must be still at server startup or the gyro bias is wrong for the whole session.
  • Unity can hold UDP ports after exiting Play mode. SimBridge diagnoses this in its bind-failure message; restart the editor.
  • The MCAP must be closed cleanly or Foxglove reports it empty. All exit paths route through shutdown() — keep it that way.

Fixing the protocol duplication

The right shape is a small shared module — say protocol.py — exporting mix(), to_pwm(), thruster_packet(), neutral_packet(), and the format strings, imported by the client, run_sim.py, and pool_test.py. C# cannot import Python, so the two Unity files stay hand-written — but a single Python source plus a test asserting the C# constants match would cut the duplication from five sites to two.

Closing note

The architecture's central bet — one command language, two interchangeable backends — is what turned scarce pool time into abundant desk time. The parts of this codebase that look over-engineered (the tuning harness, the step-test protocol, the always-on logging, the hot-reloaded gains) are precisely the parts that made that bet pay off.

The parts that look under-engineered (duplicated constants, hand-placed pixels, no tests) were traded away to buy time for the parts that mattered. That was the right trade under the constraints. Whether it stays right depends on how long this code has to live.

If you change one thing after reading this, make it the strategy brain's unit tests. It is a pure function with six inputs and five outputs, and it is the file most likely to be edited under time pressure by someone who has not slept.
