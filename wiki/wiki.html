BlueROV2 Master Technical Handoff Wiki

This master technical wiki provides an exhaustive end-to-end breakdown of the custom BlueROV2 software stack, electronics, physics simulation, kinematics, network protocols, computer vision pipeline, finite state machine autonomy, and fidelity tuning workflows.

1. System Architecture Overview

1.1 Overview & Purpose

The core objective of this codebase is to maintain a matched pair of systems for a custom 6-DOF BlueROV2 (r1) submarine:

  1. A high-fidelity physics simulator built in Unity (C#).
  2. A physical submarine hardware stack powered by a Raspberry Pi running rov_server.py.

Both systems accept the exact same 4-DOF motion commands (Surge, Strafe, Heave, Yaw), pass through an identical 6-thruster mixing matrix, and communicate over identical binary UDP socket structures. Control policies, vision state machines, and reinforcement learning models developed in simulation drop onto physical hardware with zero code modifications.

2. Submarine Hardware & Low-Level Drivers

2.1 PCA9685 PWM Generation & ESC Control (pca9685.py)

The Raspberry Pi running rov_server.py delegates hardware PWM pulse generation to an NXP PCA9685 16-channel 12-bit controller over I2C (Bus 1).

PWM Pulse Calculation

Electronic Speed Controllers (ESCs) expect a 50 Hz control signal ($T = 20\text{ ms} = 20,000\ \mu\text{s}$). The 12-bit PCA9685 resolution divides this period into 4096 ticks (0 to 4095). Microsecond pulse widths map to register tick counts via:

$$\text{Ticks} = \text{round}\left( 4095 \times \frac{\text{PWM}_{\mu\text{s}}}{20000\ \mu\text{s}} \right)$$

Sleep Mode & Prescaler Registers

To establish 50 Hz, the internal 25 MHz oscillator is scaled by a prescaler register:

$$\text{Prescaler} = \text{round}\left( \frac{25\text{ MHz}}{4096 \times 50\text{ Hz}} \right) - 1 = 121 \quad (0x79)$$

Per NXP specification, prescaler registers can only be written while the chip's sleep bit (Bit 4 of MODE1) is set. The driver executes:

# 1. Force PCA9685 into sleep mode
self.write(REG_MODE1, [MODE1_EXTCLK | MODE1_SLEEP | MODE1_AI])
# 2. Write calculated prescaler (121)
self.write(REG_PRESCALE, [prescaler & 0xFF])
# 3. Clear sleep bit to resume operation
self.write(REG_MODE1, [MODE1_EXTCLK | MODE1_AI])

2.2 MS5837 Depth & Pressure Sensor (ms5837.py)

The MS5837-30BA sensor measures piezoresistive absolute pressure via I2C (Bus 6). At boot, factory PROM calibration coefficients ($C_1 \dots C_6$) are read and validated using a 4-bit CRC check.

Second-Order Temperature Compensation

Because thermal expansion skews silicon piezoresistance underwater, second-order polynomial corrections compensate for temperatures below $20^\circ\text{C}$:

dT = D2 - C5 * 256
T = 2000 + (dT * C6) / 8388608

if T < 2000: # Below 20°C
    Ti = (11 * dT * dT) / 34359738368
    OFFi = (31 * (T - 2000) * (T - 2000)) / 8
    SENSi = (63 * (T - 2000) * (T - 2000)) / 32

Hydrostatic depth ($d$) is calculated using fluid density $\rho$ ($997\text{ kg/m}^3$ freshwater vs $1029\text{ kg/m}^3$ saltwater):

$$\text{Depth (m)} = \frac{(P_{\text{pascals}} - P_{\text{surface}})}{\rho \cdot g}$$

2.3 ICM20602 Gyroscope & Accelerometer (icm20602.py)

The ICM20602 IMU communicates over SPI (Bus 1, CS 2) at 10 MHz. SPI bitwise reads enforce high MSB (reg | 0x80).

Why Gyro Z-Integration over Compass Magnetometers?

High thruster current draws (up to 60+ Amperes) generate massive localized electromagnetic fields ($\vec{B} \propto I$) that distort magnetic compasses. Heading is instead computed by integrating bias-corrected gyro Z-rate ($\omega_z$).

At startup, 60 stationary samples calculate the resting gyro bias $\beta_z$, preventing stationary drift:

$$\text{Heading}(t) = \text{Heading}(t - \Delta t) + (\omega_z - \beta_z) \Delta t$$

3. Networking Protocols & Communications Layer

3.1 UDP Binary Struct Payload (<7H>)

Thruster packets transmit over UDP port 60000 (or 60011 in simulation) using Python's binary struct library. Format string "<7H" packs 7 unsigned 16-bit integers into exactly 14 bytes:

  • <: Little-endian ordering (ARM / x86 architecture parity).
  • 7H: 7 $\times$ 2-byte unsigned short integers (Channels 0-5 thrusters + Channel 9 light).
# Client / Sim Runner Side: Pack commands (1100 to 1900 us)
packet = struct.pack("<7H", fl_pwm, fr_pwm, rl_pwm, rr_pwm, v1_pwm, v2_pwm, light_pwm)

# Server / Unity SimBridge Side: Unpack 14 bytes instantly
fl, fr, rl, rr, v1, v2, light = struct.unpack("<7H", data)

3.2 Video Streaming Chunking & Frame Reassembly (!HHH)

JPEG encoded video frames often exceed the 1,500-byte MTU limit. rov_server.py slices JPEG byte arrays into 60,000-byte chunks prepended with a 6-byte header formatted in network Big-Endian (!HHH): Frame ID, Total Blocks, Block Index.

header = struct.pack("!HHH", fid & 0xFFFF, blocks, idx)
sock.sendto(header + chunk_payload, (client_ip, port))

Topside client maintains an asynchronous frame buffer, decoding complete byte arrays via cv2.imdecode.

3.3 Telemetry Stream Protocol (<dff>)

Depth and heading stream topside over UDP port 60001 at 50 Hz.

  • Format string: "<dff" (20 bytes total).
  • d: Double-precision float64 (Unix epoch timestamp).
  • f: Single-precision float32 (Water depth in meters).
  • f: Single-precision float32 (Integrated yaw heading in degrees).

3.4 Failsafe Watchdogs & Threading Architecture

The server runs three independent Python threads (thruster_loop, video_loop, sensor_loop). If networking drops for $>0.5\text{ s}$, thruster_loop forces all motor channels to 1500 ($\text{Neutral}$), preventing thruster runaway. Unity's SimBridge.cs enforces the exact same 0.5s timeout.

4. Kinematics, Thruster Mixing & Closed-Loop Control

4.1 Vectored Thruster Mixing Matrix

The BlueROV2 horizontal thrusters are angled at $45^\circ$. Commands $\in [-1.0, 1.0]$ map to thruster pulse outputs via:

def mix(surge, strafe, heave, yaw):
    fl = clamp(surge - strafe - yaw)
    fr = clamp(surge + strafe + yaw)
    rl = clamp(surge + strafe - yaw)
    rr = clamp(surge - strafe + yaw)
    v1 = clamp(heave)
    v2 = clamp(-heave)
    return fl, fr, rl, rr, v1, v2

4.2 Actuator Saturation & Axis Coupling

If an operator commands full forward ($\text{surge} = 1.0$) and full turn ($\text{yaw} = 1.0$), the unclipped sum for Front-Right is $1.0 + 1.0 = 2.0$. Hard `clamp(-1.0, 1.0)` clips this to $1.0$. Saturation causes axis coupling, which `ThrusterMixer.cs` reproduces in simulation.

4.3 Closed-Loop Depth PI Control

Depth holding uses Proportional-Integral feedback with anti-windup clamping to fight positive net buoyancy:

err = current_depth - hold_target
p_term = HOLD_KP * err

if abs(err) >= 0.02: # 2 cm deadband
    self._hold_i += err * dt
    self._hold_i = max(-i_cap, min(i_cap, self._hold_i))

i_term = HOLD_KI * self._hold_i
cmd = clamp(p_term + i_term)

4.4 Circular Yaw Angle Math

Angular errors wrap along the shortest arc on $S^1$ within $[-180^\circ, 180^\circ)$:

def _yaw_error(target_deg: float, current_deg: float) -> float:
    return (target_deg - current_deg + 180.0) % 360.0 - 180.0

5. Topside Software Architecture (rov_client.py)

5.1 Pygame 30Hz Event Loop & Modes

Main topside client executes a synchronous 30 Hz event loop (`clock.tick(30)`). Modes include Manual Gamepad Control, Autonomous Strategy Brain, AprilTag Mission Tracking, and Thruster Step Test Panel.

5.2 Multiprocessing Strategy (GIL Bypass)

To avoid Pygame UI frame drops caused by Python's Global Interpreter Lock (GIL), YOLO neural network inference executes in an isolated process space using multiprocessing.get_context("spawn"). Shared memory queues (`yolo_in`, `yolo_out`) with `maxsize=1` exchange frame bounding boxes asynchronously.

ctx = mp.get_context("spawn")
self.yolo_in = ctx.Queue(maxsize=1)
self.yolo_out = ctx.Queue(maxsize=1)

self.yolo_proc = ctx.Process(
    target=_yolo_worker,
    args=(weights, conf, self.yolo_in, self.yolo_out, stop_event),
    daemon=True
)

5.3 Asynchronous MCAP Data Logging

Telemetry ticks and vision detections log to Foxglove `.mcap` files protected by a mutual exclusion thread lock (`threading.Lock`), flushing buffers to disk every 1.0 second.

7.1 BoundingBox Upward Bias

Target framing aims at the top edge of the bounding box rather than center, inducing upward thrust bias that keeps the sub elevated off the pool floor:

@property

8. Unity Simulator Architecture (C# Source Code)

8.1 Hydrodynamics.cs Engine

The Hydrodynamics.cs script implements the 6-DOF Fossen underwater hydrodynamics equations within Unity's FixedUpdate() loop:

1. Restoring Forces (Weight & Buoyancy)

void ApplyRestoring() {
    Vector3 cg = rb.worldCenterOfMass;
    Vector3 cb = cg + transform.up * centreOfBuoyancyHeight;
    rb.AddForceAtPosition(Vector3.down * weight, cg, ForceMode.Force);
    rb.AddForceAtPosition(Vector3.up * buoyancy, cb, ForceMode.Force);
}

2. Effective Mass Acceleration Scaling

Because Unity's Rigidbody solver assumes a scalar mass $m_{\text{dry}}$, anisotropic added mass $\mathbf{m}_a$ is simulated by scaling applied body forces so acceleration matches $a_i = F_i / (m_{\text{dry}} + m_{a,i})$:

$$F_{i,\text{applied}} = f_i \cdot \frac{m_{\text{dry}}}{m_{\text{dry}} + m_{a,i}}$$

3. Added-Mass Coriolis & Centripetal Coupling

When translating and rotating simultaneously, linear added mass generates coupling forces and torques:

void ApplyCoriolis() {
    if (!enableCoriolis) return;
    Vector3 v = transform.InverseTransformDirection(rb.linearVelocity);
    Vector3 w = transform.InverseTransformDirection(rb.angularVelocity);
    Vector3 a1 = Vector3.Scale(addedMassLinear, v); // Linear added momentum

    Vector3 fCor = -Vector3.Cross(w, a1);
    fCor.x *= rb.mass / (rb.mass + addedMassLinear.x);
    fCor.y *= rb.mass / (rb.mass + addedMassLinear.y);
    fCor.z *= rb.mass / (rb.mass + addedMassLinear.z);
    rb.AddForce(transform.TransformDirection(fCor), ForceMode.Force);

    Vector3 tCor = -Vector3.Cross(v, a1);
    rb.AddRelativeTorque(tCor, ForceMode.Force);
}

8.2 SimBridge.cs UDP Layer

SimBridge.cs acts as the network port-mirror layer. It receives thruster UDP packets (<7H>) on port 60011, inverts the thruster mix to recover surge/strafe/heave/yaw, and projects the target sub into 640x480 screen coordinates to stream 16-byte UDP bounding boxes (<4f>) on port 60010.

8.3 ThrusterMixer.cs Parity

ThrusterMixer.cs provides a static C# struct and mixing method matching Python's mixing matrix 1:1:

public static ThrusterOutput Mix(float surge, float strafe, float heave, float yaw) {
    return new ThrusterOutput {
        fl = Mathf.Clamp(surge - strafe - yaw, -1f, 1f),
        fr = Mathf.Clamp(surge + strafe + yaw, -1f, 1f),
        rl = Mathf.Clamp(surge + strafe - yaw, -1f, 1f),
        rr = Mathf.Clamp(surge - strafe + yaw, -1f, 1f),
        v1 = Mathf.Clamp(heave, -1f, 1f),
        v2 = Mathf.Clamp(-heave, -1f, 1f),
    };
}

8.4 TuningHarness.cs Solvers

TuningHarness.cs contains an offline nested bisection solver (40 outer iterations for drag scale, 40 inner iterations for thrust gain) that calculates exact hydrodynamic gain adjustments from real pool pulse test measurements (powered distance + coasting glide).

8.5 RandomSpawn.cs Logic

RandomSpawn.cs teleports submarine GameObjects on Play start inside volume `areaCenter = (0, 1.5, 0)` and `areaSize = (13, 2, 13)`, applies random yaw rotation, zeros velocity, and synchronizes transforms.
